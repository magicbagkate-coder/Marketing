## 1.1 Линтер — главный страж правил
Правила кода из раздела 5 переведены в `eslint.config.mjs`. Ассистент после каждой правки кода обязан:
1. запустить `npm run lint` (сам исправляет что может: порядок импортов и т.п.);
2. если остались ошибки — исправить код, а не ослаблять правило и не добавлять `eslint-disable`;
3. запустить `npm run build` и убедиться, что сборка проходит.

Менять `eslint.config.mjs` можно только по прямой просьбе владелицы. Что линтер **не** проверяет (следить самому): имена из двух слов, JSDoc на публичном API, i18n и отсутствие магических строк, «не больше 5 наследников / производных type», тесты для security/auth.

## 3. Как работать с владелицей
- Ничего не создавать и не запускать, пока нет задачи. Перед крупной фичей кратко описать структуру модулей и дождаться «да».
- Отвечать по объёму задачи: на простой вопрос — коротко, на сложную задачу — подробно.
- Объяснять простыми словами, без лишнего жаргона. Владелица — не программист.
- Не сдаваться после первой ошибки: разобраться в причине, исправить; если не выходит — честно сказать, что не получилось и почему.
- Команды (install, build, lint, test) выполнять самому, не просить владелицу.
- Действия «вовне» (отправка сообщений клиентам, публикация постов, изменения в CRM, покупки) — только после явного «да» владелицы.

## 4. Безопасность
- Не коммитить секреты, API-ключи и токены. Хранить только в `.env` / `.env.local`, файлы с секретами добавлять в `.gitignore`.
- Если в staging попал `.env` или ключ — предупредить сразу.
- Данные клиентов (имена, телефоны, адреса, переписки) — не логировать без необходимости и не отправлять в сторонние сервисы.
- Критично: security / auth — тесты до merge в main.

## 5. Правила кода (для нового бота)

### Цель правил
- Человек не удерживает в голове больше 3–4 цепочек логического ветвления. Дальше падает поддержка и растёт риск багов.
- Все правила — в первую очередь ради KISS: код должен читаться и меняться без «распутывания» логики.
- Лимиты (ветвления, строки в файле, наследники, аргументы функции) — защита от перегруза головы, а не бюрократия.
- Два решения равны по задаче — выбирать проще. Исключение: security / auth (безопасность важнее краткости).

### Если правила спорят между собой
- Цель правил (KISS, лимит ветвлений) — ориентир при любом выборе.
- Критичные запреты (any, interface, сложные utility-type, security/auth без тестов) выше KISS, не ослаблять.
- Новый код и рефакторинг — по всем правилам.
- Правка legacy без рефакторинга — минимальный diff и стиль соседнего кода; не добавлять interface, any, default export; существующий else / interface не трогать, новый код в том же файле — без else и interface.
- Не раздувать: меньше 50 строк и одна задача — не дробить файл без причины.

### Язык и локализация
- Весь новый код — на английском: исходники, комментарии, сообщения коммитов, документация.
- Существующий код с другим языком не трогать без рефакторинга.
- Без захардкоженных UI-строк и текстов для клиентов — отдельный слой i18n (translations, locales). Ключи на английском.

### Зависимости
- Перед крупной задачей проверить, есть ли готовый проверенный модуль. Не писать своё для типовых доменов (Excel, PDF, crypto, HTTP-клиент, OAuth, сложный парсинг).
- Мелкие утилиты (1–2 функции) и бизнес-логику магазина — писать самим, пакет не искать.
- После добавления пакета: depcheck (неиспользуемое), npm audit (CVE), проверить репутацию и активность; в описании изменений 1–2 предложения, зачем выбран и какие альтернативы смотрели.
- Неиспользуемые зависимости удалять из package.json.

### Архитектура и качество
- Файл — не более 250 строк. При превышении разбивать на модули.
- Классы: у одного базового класса не более 5 прямых наследников; у класса не более одного `extends`; `implements` — по минимуму.
- Больше 10 case по одному значению — Map или отдельный файл стратегии, не длинный switch.
- SOLID, Clean Architecture, Strategy / Factory / Observer — только если упрощают код.
- Декларативный стиль, без callback hell и глубокой вложенности.
- SRP: у модуля, компонента или функции одна зона ответственности.
- JSDoc для публичного API (сервисы, стратегии, shared utils).
- Имя файла = главный экспорт; один файл — одна публичная сущность.
- Разные слои и точки входа (API, фоновые задачи, CLI, интеграции) — отдельные файлы.
- Общие type — в отдельный файл, если используются в 2+ местах или больше ~30 строк.

### Принципы реализации
- Минимальный diff: самый маленький корректный объём изменений, лишний код не трогать.
- Без переусложнения: никаких преждевременных абстракций, хелперов на один вызов и обработки нереальных кейсов.
- Комментарии только для неочевидной логики, плюс JSDoc на публичный API.
- DRY в runtime-коде и явных type; KISS — главная цель; YAGNI — не добавлять то, без чего код и так понятен.
- При рефакторинге старый код можно закомментировать рядом; после merge удалить (история в git).

### Имена
- Переменные и функции — из двух слов; короткие имена только для локальных и общепринятых (id, url, index).
- Запрещены безликие имена: handler, handle, process, data, temp. Имя говорит, что делает.
- camelCase для JS/TS; в других языках — по принятым в языке правилам.

### Сложность
- Законченное ответвление — не более 4 позиций (if / switch / цикл / тернарник; `&&` и `||` в строке не считаем). Один switch = одна позиция, case внутри — не больше 10.
- Критично: функция с больше чем 3 аргументами — один объект-параметр.
- `else` запрещён в новом коде — ранний return, ветки завершают сценарий явно.
- Inline guard: если тело `if` — только ранний выход (return, continue, break) и условие в одну строку, писать одной строкой без фигурных скобок.
- Соблюдать ESLint и lint-правила проекта.
- Больше 3 `if` по одному значению — switch (до 10 case, дальше Map).
- Map / Set — когда нужен частый lookup или уникальность, не везде.
- Предпочитать map, filter, reduce вместо ручных циклов, где читается лучше.

### TypeScript (если стек будет TS)
- `any` запрещён — `unknown` + явное сужение.
- Публичные функции — явный возвращаемый type.
- Только именованный export, default export запрещён.
- Формы объектов и контракты — только через `type`. `interface` запрещён в новом коде.
- Критично: производные type — один слой одного utility от базового type: Partial, Required, Readonly, Pick или Omit.
- Критично запрещено: цепочки utility, несколько utility на одном type, Record, Exclude, Extract, Awaited, ReturnType, conditional types, mapped types, template literal types, intersection и union для сборки object type, сторонние type-хелперы. Union примитивов и string literal union (status, action) разрешены.
- От одного базового type не более 5 производных. Больше — разбить базовый type или ввести именованный промежуточный.
- Комбинация полей — явный type или несколько именованных type, не вложенные utility.

### Организация
- Константы по доменам; без магических строк в коде.
- Импорты: внешние пакеты, затем types, затем локальные модули; между группами пустая строка.
- async/await, не цепочки `.then`.
- `catch` не пустой: ошибки не глотаем, логируем или пробрасываем с контекстом.
- `console.log` только в разработке; в production — логгер.

### Тесты
- Обязательно: security / auth.
- При изменении нетривиальной логики (парсинг, нормализация, агрегации, публичный API) — тесты в том же изменении.
- Прочее — по запросу или если поведение неочевидно из кода.

### Стек и окружение
- Стек зафиксирован в разделе 1 (Node.js, NestJS, TypeScript, без БД, dotenv, алиас `@/`). Не добавлять новые технологии без согласования.
- Новый npm-скрипт — одна строка в README в том же изменении. Отдельные md-файлы — только по запросу владелицы.

### Git и поставка
- Коммиты только по явной просьбе; сообщение про «зачем», а не список файлов.
- Изменения небольшие; test plan, если менялась логика из раздела «Тесты».

### Поведение ассистента при написании кода
- Чистый поддерживаемый код, не одноразовые хаки.
- Перед крупной фичей кратко описать структуру модулей.
- Команды install, build, lint, test выполнять самому.
